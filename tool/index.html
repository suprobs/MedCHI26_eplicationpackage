Expert reference library — extraction check & reuse

Curated .md tables built by the expert from analyzing many manuals of the device class: component nomenclatures and their variants, procedures, errors, and cross-device action archetypes. When loaded, every extracted name is compared against the library — exact / known variant / partial / unknown — plus a list of what the library expects but the extraction missed. The check is informational: it never blocks the flow. Files are read automatically from a library/ folder inside the selected root folder, or you can drag them here.

components · procedures · errors · archetypes — several files or one combined file
Expected table formats

Components / procedures / errors: the same tables Prompts 1–3 produce. The easiest way to build the library is to run Prompt 1 (and 2/3) over a large corpus of manuals of the device class and save Block 2 (full working table). The first header cell identifies the table type (Element, Procedure, Error / fault); a Name variants column, if present, is used as the alias list, and a parenthetical in the name — Water tank (reservoir) — also counts as a variant.

Action archetypes (cross-device reuse): a table whose first header cell is Archetype:

| Archetype | Action verbs | Component keywords | Movement | Core script | Notes |
|---|---|---|---|---|---|
| hinged_cover_open | open, lift, raise, flip | lid, cover, top tray, lever | hinge | ConstrainedMover (FlipHinge) | printer top cover ≈ coffee machine lever |
| press_control | press, push, tap | button, control, switch | press | EfsmPressTrigger | |
| insert_consumable | insert, place, load | capsule, cup, paper, cartridge | press | EfsmStickToTarget | attaches at end pose |

Movement uses the matrix vocabulary hinge · press · static (a slide counts as hinge for grab purposes — the actual slide trajectory is defined in the Device Spec screen). Core script names the existing EFSM core script the archetype reuses; the library recommends configuration of existing binders, never new code.

②·c Movement trajectories (initial → final pose per component)

For each grabbable component, define the initial and final pose of its movement: press a Capture in preview button and drag the part in the preview above (the angle slider rotates it in the chosen plane), or type the values directly as an alternative. The generated behavior configuration constrains the grab movement to exactly that trajectory: a rotation between poses becomes a hinge (pivot computed automatically from the two poses) and a translation becomes a linear slide along the dominant axis. The lateral checkbox marks parts that attach to another component at the end pose. Defaults are pre-filled from the manual (EFSM movement vocabulary, categories and locations): lids/levers open about their hinge edge, trays slide out, and consumables (capsule, paper, cup) start free-floating and end attached to their receptacle. Inferred defaults carry provenance target_manual:inferred_trajectory; any edit promotes them to user_decision.

Reasonable defaults are already filled in from the manual. Click a part in the legend above, then use Capture in preview and drag it to where it should start and end.

②·d Cross-device reuse (reference library archetypes)

Each interactive component is matched — deterministically: action-verb + component-keyword similarity, score shown — against the library’s action archetypes. Example: opening a printer’s top cover and opening a coffee machine’s lever are the same hinge archetype handled by the existing ConstrainedMover. Matches pre-fill the movement in the matrix above with provenance library_match (LIB tag); review them here and apply or dismiss each one — dismissing restores the heuristic inference. Suggestions reuse existing core scripts: configuration, not new code. Auto pre-fill never downgrades a component to static.

The library recognizes movements it has seen in other devices and pre-selects them. Check the list and dismiss any that look wrong.

②·e Whole-device check (represented object vs. the manual)

The simulated object is the whole device, not only the parts this procedure drives. Every component the manual describes is built as geometry; the procedure decides only which parts are interactive. Compare the roster below against the labelled overview figure in the manual and confirm it’s complete. Missing parts or parts placed only by archetype fallback are flagged. This confirmation is required before validation.

Check that the built device matches the picture in the manual. Load the manual’s overview figure to compare side by side, then confirm.

How the simulation works
1
When entering Play Mode, the EfsmStateManager initializes the EFSM and activates step 1 of the procedure.
2
The floating canvas shows the user the instruction for the active step and visually highlights the component to interact with.
3
The user grabs and moves the component with their tracked hands. The ConstrainedMover restricts the movement to the axis and range defined in the EFSM.
4
When the component reaches the snap threshold (85% of the travel), the EfsmComponentBinder fires the state transition and emits the corresponding signal.
5
The EfsmStateManager receives the signal, checks the step's postcondition, and advances to the next step on the canvas.
6
When the last step is completed, the canvas shows the «Procedure completed» message and the simulation ends.
